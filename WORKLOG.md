## Архитектурные решения

### D1. Конфиг версии хранится как неизменяемый JSON-снимок
`funnel_versions` пишется только через INSERT, `config_json` хранит файл как есть. Структура шагов живёт внутри JSON, поэтому новая
версия (новый шаг, результат, событие) — это новая строка, а не миграция схемы. Альтернатива «нормализовать шаги в таблицы» ломалась бы на каждом п.8.

### D2. Активная версия — указатель плюс журнал, откат = новая запись
`funnel_active` указывает, на какой версии создаются новые сессии, а `release_log` пишется только через INSERT. Rollback переключает
указатель на `from_version` последней неотменённой публикации и ничего не удаляет, поэтому аудит и аналитика прошлых версий сохраняются.

### D3. Версия и вариант закрепляются за сессией навсегда
`sessions.funnel_version` и `variant` пишутся один раз при создании. После публикации или отката начатые сессии дописываются
на своей версии (моё решение), новые создаются на активной. Альтернативу «переводить сессии на новую версию» отклонили:
она смешивает аналитику версий и требует маппинга шагов.

### D4. Общий движок в packages/shared для клиента и сервера
Условия, навигация, валидация и расчёт результата — чистые функции, которые используют и React, и сервер. Клиент получает
мгновенный UX, а сервер перепроверяет state и сам считает результат, так что подделать результат с клиента нельзя и логика не расходится.

### D5. Идемпотентность событий: INSERT … ON CONFLICT DO NOTHING, а не upsert
Событие — неизменяемый факт, первая запись побеждает. Upsert позволил бы ретраю с изменённым payload перезаписать данные.
Пачка обрабатывается по событию: невалидное получает `rejected{reason}` и не мешает остальным.

### D6. Контекст события (версия, вариант, UTM) проставляет сервер из сессии
Клиент присылает эти поля (так требует ТЗ), но сервер сверяет их с сессией, а в БД пишет значения из сессии. Так аналитику
нельзя испортить багом клиента или подделкой.

### D7. Агрегаты — множества уникальных сессий, порядок только по клиентскому seq
Все метрики строятся как COUNT DISTINCT session_id по наличию событий, поэтому дубли и порядок прихода на них не влияют. Порядок
нужен только для «последнего просмотренного шага» (отвал), и его задаёт монотонный `seq` клиента, а не `server_ts`.

### D8. A/B: детерминированный хеш при создании, override только создаёт новую сессию
`sha256(experiment_id:session_id) mod Σweight` воспроизводим и тестируем. Override не мутирует существующую сессию, иначе
её события разъехались бы по двум вариантам; такие сессии помечены и исключаются из A/B-сравнения по умолчанию.

### D9. Новое событие v3 — сначала код с проверкой по allowed, потом публикация конфига
Клиент отправляет событие, только если оно есть в `events.allowed` версии своей сессии. Поэтому код отправки
`recommendation_expanded` можно выкатить заранее, и для v1/v2 он ничего не делает, а v3 потом публикуется из админки без деплоя.
Код пишется во второй итерации (по ТЗ v3 — вторая итерация).

## Ход работы

### Шаг 0 — каркас (chore)
npm workspaces (`packages/shared`, `apps/server`, `apps/web`), TypeScript 6 strict + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`,
Vitest, ESLint с `no-explicit-any: error`. Конфиги закоммичены байт-в-байт; sha256 после коммита совпадает с исходным.

### Шаг 1 — общий движок `packages/shared` (feat)
Сделано: zod-схема конфига, `evaluateCondition` (10 операторов + all/any/not), `resolveVariant` (deep-merge overrides),
`computeVisibility`/`nextStepId`/`computeProgress`/`computeResult`, `validateAnswer` с fallback сообщений, `validateState`
(серверная перепроверка state), `validateConfig` (ссылочная целостность), схема события и privacy-фильтр свойств. 57 unit-тестов.

- **D10. Видимость считается за один проход по sequence.** Условие шага вычисляется на «эффективных» ответах предыдущих видимых
  шагов. Это точно, потому что валидатор запрещает условия, ссылающиеся вперёд. Ответ скрытого шага остаётся в state (вернётся при
  повторном открытии ветки), но не влияет на результат и прогресс — иначе снятый «compliance» всё равно давал бы `regulated_scale`.
- **D11. Отсутствующий ответ делает любой лист условия ложным**, даже `neq`/`not_in`. «Ещё не ответил» не должно открывать ветку;
  если нужно обратное, в конфиге есть явный `not`.
- **D12. Схема zod «loose» для метаданных и строгая для того, что исполняется.** Неизвестные поля (`releaseNote`) проходят, а
  неизвестный тип шага или оператор — нет: такой конфиг не опубликуется, и рантайм никогда не встретит то, что не умеет рендерить.
- **D13. Сообщения валидации с fallback.** В конфигах нет `required` у `priorities` и нет текста для дробного числа при `step: 1`;
  цепочка «свой ключ → родственный ключ → общий текст» гарантирует, что пользователь всегда видит понятное сообщение.
- Проверено: все три реальных конфига проходят `validateConfig` без ошибок и предупреждений; каждый негативный тест падает
  **по своей причине** (тест сверяет текст ошибки). Отклонение от плана: битые конфиги для негативных тестов не лежат файлами в
  `tests/fixtures`, а строятся мутацией реального v1 в тесте — так видно, что именно сломано, и фикстуры не устаревают.
- Ревью своего вывода: `tsc` по тестам (отдельный `tsconfig.test.json`) нашёл 2 ошибки типов в таблицах `it.each`, которые Vitest
  не ловит (он не проверяет типы). Исправлено явной типизацией таблиц; `npm run typecheck` теперь включает тесты.

### Шаг 2 — сервер, БД, версии (feat)
Сделано: Fastify-приложение, SQLite (better-sqlite3, WAL, foreign keys, таблицы `STRICT`), раннер миграций при старте,
`VersionsService` (upload / publish / rollback / list), админ-API под `x-admin-token`, seed v1 на пустой БД,
`GET /api/admin/schema` и `npm run db:schema-hash` (отпечаток схемы), CLI `npm run publish-config`. 7 интеграционных тестов (тест 4 ТЗ, часть про версии).

- **D14. Миграции — в коде, применяются автоматически при старте** (`schema_migrations`). Цель схемы — чтобы новые версии
  воронки не требовали новых миграций вообще; раннер нужен только для эволюции самой платформы и исключает «ручной SQL».
- **D15. Идентичность версии = (funnelId, version) из файла + sha256 канонического JSON.** Повторная загрузка того же файла —
  no-op (удобно для ретраев CLI), а тот же номер с другим содержимым — 409: иначе сессии, закреплённые за версией, могли бы
  внезапно получить другой конфиг. Поле `status` из файла игнорируется: активность хранит сервер (D2).
- **D16. Rollback — это стек по `release_log`.** Отменяется последняя неотменённая публикация. Так «v1→v2→v3→rollback→rollback»
  честно возвращает v2, затем v1, а первую публикацию отменить нельзя (409), потому что до неё ничего не было.
- **D17. Кэш распарсенных конфигов без инвалидации.** Строки `funnel_versions` никогда не меняются, поэтому кэш по ключу
  `funnel@version` корректен всегда и снимает парсинг JSON с горячего пути сессий и событий.
- Дополнение к модели данных: в `events` добавлена колонка `assignment` (hash/override), чтобы исключать override-сессии из
  A/B без JOIN с `sessions`.
- Проверено вживую: сервер стартует, v1 засеивается; `publish-config funnel-v2.json` → активна v2 → `--rollback` → активна v1;
  `schemaHash` до и после одинаковый (`2165016e…`).

### Шаг 3 — сессии, A/B, закрепление версии (feat)
Сделано: `POST /api/sessions` (активная версия + назначение варианта + серверный `session_started` в одной транзакции),
`GET /api/sessions/:id` (конфиг **закреплённой** версии с применённым вариантом), `PUT …/state` (перепроверка общим движком +
optimistic lock по `rev`), `POST …/result` (результат считает сервер), TTL 72 ч → 410. 11 интеграционных тестов (тесты 1, 2 ТЗ и
часть теста 4 про сессии).

- **D18. `session_started` пишет сервер, в той же транзакции, что и сессия, с id = uuid v5(session_id).** Так событие не может
  потеряться (нет сессии без старта и старта без сессии) и не может задвоиться — это знаменатель всех конверсий.
- **D19. Клиент не выбирает результат.** `POST /result` проверяет, что все видимые вопросы отвечены (та же `validateState`), и
  считает правило по сохранённым ответам закреплённой версии. На v2-сессии после отката на v1 получаем `meeting_heavy` — правило,
  которого в активной v1 нет.
- **D20. Optimistic lock на state (`rev`) вместо «последний победил».** Две вкладки одной сессии не затирают ответы друг друга:
  устаревшая получает 409 с актуальным состоянием.
- **D21. Кэш собранной воронки по (версия, вариант)** — безопасен по той же причине, что D17.
- **Мутационная проверка тестов** (чтобы убедиться, что тесты ловят то, что заявляют): (1) подменил в `GET` версию сессии на
  активную → тесты 1 и 4 упали; (2) сделал назначение варианта случайным → тест детерминизма упал. После возврата кода всё зелёное.

**Дизайн-ревью: блокирующих проблем нет; принятые изменения в план** (реализуются в соответствующих шагах):
- **D22 (меняет утверждённое определение). Отвал = самый дальний достигнутый шаг** (максимальная позиция в sequence варианта
  среди просмотренных), а не «последний по seq». Причина: при back-навигации «последний» противоречит колонке «дошли до шага»
  и зависит от порядка/часов; «самый дальний» не зависит от порядка по построению (так считает Amplitude). Инвариант
  `Σ отвалов + дошли + в процессе = начали` сохраняется.
- **D23. Корзина «в процессе»**: сессия без результата, не истёкшая, с активностью за последние 30 мин не считается отвалом.
- **D24. Статистика A/B**: Wilson-интервалы, минимально детектируемый эффект (при ~75 на плечо ≈ 23 п.п. — на дашборде
  явно «не значимо ≠ нет эффекта»), проверка SRM (χ² по A/B), guardrail — паритет распределения `result_id` между A и B
  и доля back. В README — что B объединяет несколько изменений, и что формулировка CTA у B разная в v1/v2/v3.
- **D25. Трафик генератора помечается** (`utm_source=trafficgen`, `utm_content=<runId>`), `--verify` сверяет только свой срез —
  иначе ручные клики проверяющих ломают сверку.
- **D26. Сверка событий с серверными фактами**: на дашборде «дошли (по событиям)» рядом с «завершили (сервер)» — видно потери.
- **D27. Outbox**: пачки режутся по байтам (лимит keepalive 64 КБ), 413 → делим пачку, ретрай только на сеть/5xx;
  счётчик «конфликтующих дублей» (тот же event_id, другой payload). Один путь отправки `back_clicked` (кнопка UI и popstate
  не должны давать два события), защита от двойного `step_viewed` в React StrictMode.
- **D28. Приватность**: ответы в `sessions.state_json` очищаются после истечения TTL. `next_step_id`/`destination_step_id`
  косвенно раскрывают ветку (например, выбор compliance) — оставляем, так как свойства требует конфиг, и документируем.
- **D29. Fly**: `min_machines_running = 1` (без холодного старта у проверяющего), снапшот volume перед итерацией 2. _Позже Fly.io заменён на Railway — см. «Хостинг» в конце журнала._

  «число событий по версиям не уменьшилось, метрики сессий, завершённых до публикации, идентичны, schema hash тот же».
- Для итерации 2 учтено: `recommendation_expanded` отправлять при фактическом рендере раскрытого блока (не при сворачивании);

### Шаг 4 — рантайм воронки на React (feat)
Один компонент на **тип** шага (info / single / multi / number / result), всё содержимое из конфига. `useFunnel`:
возобновление сессии из localStorage или создание на активной версии; `?variant=` другого варианта → новая сессия (D8);
навигация общим движком; каждое действие сохраняется на сервер (последовательно, с `rev`); история браузера зеркалит путь
воронки, поэтому системная кнопка «назад» работает как Back — **один путь кода** (popstate), двойного `back_clicked` нет;
после refresh история браузера восстанавливается из сохранённого пути. Результат запрашивается у сервера после завершения всех
сохранений; экран результата использует `loadingTitle/errorTitle/retryLabel` из конфига; CTA раскрывает рекомендации.
Outbox событий в localStorage: пачки по количеству и байтам (<48 КБ из-за лимита keepalive 64 КБ), 413 → пачка делится,
ретраи с backoff на сеть/5xx, отправка на `pagehide`/`visibilitychange`. Клиент шлёт только события из `events.allowed` версии сессии.

**Проверено вживую в браузере** (dev-серверы): валидация с текстами из конфига («The team must have at least one person.»,
«Enter a whole number.», «Choose no more than three priorities.»); ветка hybrid → вопрос про офис, прогресс 6→7; refresh
посреди анкеты → тот же шаг и прогресс, браузерный «назад» после refresh возвращает на предыдущие шаги с сохранёнными ответами;
смена на remote → вопрос про офис пропущен, прогресс 7→6; результат `async_native` (remote + разные часовые пояса), CTA раскрыл
рекомендации; в БД 44 события сессии с корректными `seq`, back_clicked и повторными step_viewed.

**Найдено и исправлено при ручной проверке (свои баги):**
1. Браузерная валидация `min`/`step` блокировала отправку формы и показывала системную подсказку вместо текста конфига → `noValidate`.
2. React StrictMode запускал bootstrap дважды → создавались **две сессии**, пустая исказила бы «начали» → общий in-flight
   промис на воронку; проверено: одна сессия на заход.
3. Гонка при быстрых кликах: ответ сохранения перезаписывал локальное состояние более старым → из ответа берётся только `rev`.
4. `step_viewed` терялся при возврате на тот же шаг (ключ дедупликации «шаг+глубина» совпадал) → номер навигации `navId`.
5. `whenSaved` пересоздавался каждый рендер → бесконечные запросы результата → `useCallback`.
Ложная тревога, записанная честно: UTM «не сохранились» только потому, что инструмент браузера открыл URL без query;
при прямом заходе UTM и override сохраняются (проверено через API и в браузере).

### Шаг 6 — аналитика (агент) + дашборд и админка (я)
**Модуль аналитики сделал агент в изолированном worktree** (ветка влита merge-коммитом `928ef35`, в истории видна
параллельная работа). Перед слиянием я прочитал код целиком: определения совпадают со спецификацией, инвариант
`Σ отвалов + до первого экрана + дошли + в процессе = начали` проверяется и выводится. Формулы статистики (Wilson,
Newcombe, z-тест, MDE, SRM) сверил с источниками. 19 новых тестов (тест №5 ТЗ + статистика), всего 119.
Решения агента, которые я принял: `stepConversion = passed/viewed` (а не «к предыдущему шагу» — иначе условный шаг
выглядит как потеря); SRM считается только по hash-сессиям; тай-брейк результата по `event_id` для детерминизма.
Отмеченные агентом риски и моё решение:
- `ingest_log` глобальный, без funnel_id — **принято как ограничение** (одна воронка в проекте), на дашборде подпись «all batches».
- поздний ретрай события на 30 минут «оживляет» сессию в «в процессе» — **принято**, описано в README.
- нельзя отфильтровать сессии без кампании — **принято**, низкий приоритет.
- установка better-sqlite3 из исходников на Windows (нет prebuild под Node 22.22 для VS 18) — у меня модуль уже собран;
  в Docker (Linux) есть готовые бинарники. Учтено для деплоя.
Типы отчёта перенесены в `packages/shared/src/analytics.ts`, чтобы сервер и дашборд использовали один контракт.

**Дашборд `/analytics`** (публичный, D30): KPI по вариантам, карточка A/B (Wilson CI, разница с CI, p-value, MDE, SRM),
воронка по шагам в порядке каждого варианта с бейджем «conditional», распределение результатов, сравнение версий,

- **D31. Предупреждение о малой выборке.** При <30 сессий в группе дашборд прямо пишет, что выводы делать нельзя, даже если

### Шаг 7 — генератор трафика (feat)

- **D32. Окно «в процессе» — параметр отчёта** (`in_progress_minutes`, по умолчанию 30, на дашборде переключатель,

- **D33. Проверка генератором независимым расчётом.** Генератор сам ведёт ground truth (что реально доставлено) и считает
  started / reached / CTA / до первого экрана / отвал по шагам своим кодом, затем сравнивает с **дельтой** отчёта до/после
  прогона (окно 0). Результат прогона seed 42: **24 из 24 показателей совпали** при 2848 событиях, 617 отброшенных дублях
  (145 повторных пачек), 128 перемешанных и 18 переставленных пачках, 72 отклонённых битых событиях.
- По умолчанию один поток: генератор со случайным сидом тогда воспроизводим по поведению (варианты A/B назначает сервер

- Наблюдение для README: модель задавала B чуть лучше, а на 150 сессиях B вышел на 4.4 п.п. хуже (p = 0.52, MDE ≈ 19 п.п.) —
  наглядная иллюстрация, почему на такой выборке нельзя делать вывод, и зачем дашборд показывает MDE.

## Русская локализация (i18n) — продуктовое решение
- **D35. Перевод контента воронки — отдельным словарём, ключ = исходная английская фраза (gettext-подход).**
  Конфиги заказчика редактировать нельзя, поэтому тексты вопросов, вариантов, сообщений валидации и результатов

Заказчик спросил, почему всё открыто и логично ли расположена админка. Разбор по ТЗ: про авторизацию в ТЗ ничего нет,

## Хостинг: Railway вместо Fly.io

Fly.io требует консольной программы `flyctl`, а на рабочей машине нельзя ничего устанавливать; ТЗ хостинг не задаёт.
Railway разворачивается из браузера прямо из GitHub-репозитория, собирает тот же `Dockerfile` и даёт постоянный volume
для SQLite. Render отклонён: на бесплатном тарифе диск не сохраняется между перезапусками, база бы стиралась.
`fly.toml` удалён (он противоречил бы README; история в git). Настройки — `railway.json`: сборка из Dockerfile,
health-check `/api/health`, перезапуск при сбое, пересборка только при изменении кода (правка документации не кладёт
сайт, пока его смотрят). Volume `/data`, `ADMIN_TOKEN` (новый, не тот, что использовался при разработке) и
`TRUST_PROXY=1` задаются в настройках сервиса: без `TRUST_PROXY` все посетители за прокси Railway делят один лимит
запросов, а cookie входа не получает `Secure` (второе теперь закрыто и в коде).

## Обновление без заметного простоя (вместо blue-green)

Просили blue-green с балансировщиком, чтобы сайт не пропадал при обновлении. С SQLite (требование ТЗ, как и запрет
сторонних сервисов) обе копии должны писать в один файл — это возможно только на одной машине, а Railway подключает
volume к одному контейнеру и при деплое останавливает старый до запуска нового. Варианты: свой VPS с Caddy и двумя
копиями на общем volume (настоящий blue-green, но платно и дольше) или Postgres (нарушает ТЗ). Выбрано: Railway +
«незаметный перезапуск» — health 503 и `Connection: close` во время остановки, дренаж запросов, старт ~1 с, health-check
перед подачей трафика; в браузере service worker с оболочкой сайта и файлами версии, повторы идемпотентных запросов
до ~15 с, очереди сохранения и событий; перезагрузка страницы, если после деплоя запрошен уже удалённый файл. Проверено
выключением сервера посреди анкеты на production-сборке.

## CI перед деплоем

Railway уже выкатывает каждый push в `master` (CD), но без проверки сломанный коммит сразу попал бы на сайт. Добавлен
GitHub Actions: `npm ci`, typecheck, lint, тесты, сборка и `npm audit --omit=dev --audit-level=high` на каждый push и
pull request; в Railway включается «Wait for CI», и деплой идёт только после зелёной проверки. GitHub Actions работает
на стороне GitHub и не участвует в работе приложения, поэтому не противоречит «никаких сторонних сервисов».
Config-as-code Railway для новых сервисов больше не подключается — настройки продублированы в интерфейсе.

## Тестовая стратегия и CI уровня команды

Ориентир — «testing trophy»: больше всего интеграционных тестов, модульные для чистой логики, немного E2E на
ключевые пути; плюс практики CI GitHub Actions (SHA-пины, минимальные права, отмена устаревших прогонов).
- **Property-based (fast-check)** для движка и статистики: законы, которые должны выполняться для любых ответов, а не
  для трёх примеров. Первая версия свойства «скрытые ответы не влияют на результат» не ловила намеренную поломку: в
  реальных конфигах правило на условный вопрос всегда содержит и его условие. Добавлен конфиг с правилом прямо на
  `office_days` — теперь поломка ловится с минимальным контрпримером.
- **Компонентные тесты** (Testing Library + jsdom) по ролям и подписям: шаги из реального конфига, экран результата,
  очередь событий на поддельном `fetch` и таймерах, свайп. `matchMedia` в jsdom отсутствует — добавлена заглушка
  «ничего не совпадает», как в обычном браузере.
- **E2E (Playwright)** на production-сборке с чистой базой; путь посетителя проверяется до цифр дашборда. Локально
  используется установленный Edge (ничего не скачивается), в CI — Chromium Playwright. Аудит WCAG 2.2 AA (axe).
- **Smoke-тест Docker-образа**: впервые образ из текущего кода собран и проверен целиком (у Docker появился доступ в
  сеть): uid 1000, заголовки, `traffic --verify`, SIGTERM → код 0, данные после рестарта.
- **Каждый новый вид тестов проверен мутацией** (намеренной поломкой кода): тесты падают, код восстановлен.
- **Не сделано:** автоматическое мутационное тестирование (Stryker) — долго для каждого push; CodeQL — для приватного
  репозитория нужен платный GitHub Advanced Security.

## Ревью CI и тестов (два агента) перед отправкой

**CI:** блокеров нет. Исправлено: аудит зависимостей вынесен в отдельный `audit.yml` (свежая уязвимость в чужой
библиотеке не блокирует деплой `master`); на `master` прогоны не отменяются (виден коммит, который сломал); шаг сводки
покрытия не падает вторым после упавших тестов; Dependabot не предлагает мажорный Node в образе (CI проверяет на 22);
`persist-credentials: false`, исполняемый бит скрипта, тесты и отчёты исключены из контекста Docker. Честно
переписано: защита ветки на бесплатном GitHub для приватного репозитория недоступна — барьер обеспечивает Railway.

**Тесты:** ревьюер сделал 11 мутаций, 3 выжили — это были реальные дыры:
| Не ловилось | Что добавлено |
|---|---|
| видимость шага по скрытым ответам (в v1–v3 все условия смотрят на всегда видимые вопросы) | конфиг с вопросом, открываемым условным `office_days`, и свойство «скрытые ответы не меняют видимые шаги» |
| удаление всей пачки на 200 вместо подтверждённых событий | тест частичного подтверждения: неподтверждённое уходит повторно с тем же id |
| события прошлой загрузки не отправляются | тест: они уходят первыми, как только страница что-то отслеживает (очередь создаётся при первом событии) |
| «законы трёхзначной логики» (двойное отрицание, де Морган) выполняются и для двузначной | свойство монотонности: решённое условие не меняется от ответа на новый вопрос — ловит обе мутации |
Также: аудиты доступности ждут нужный экран (раньше могли проверять предыдущий); цикл «до результата» ограничен и
отличает результат от экрана загрузки; в E2E первый ответ сервера на пачку событий «теряется», и тест проверяет, что
дубли отклонены, а сессия посчитана один раз; `result_viewed` «один раз» проверяется в React StrictMode; точные пороги
свайпа (79/80 px, 23/24 px); назначение вариантов по весам на 20 000 сессий; дашборд и версии в аудите доступности —
**найдена и исправлена настоящая ошибка**: у полей загрузки конфига на странице версий не было подписей.
