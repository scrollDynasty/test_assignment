# Funnel Runtime

Мини-платформа для многошаговых веб-воронок: экраны описываются JSON-конфигом, у конфига есть версии с публикацией и
откатом без передеплоя, внутри версии работает A/B-эксперимент, события собственного endpoint'а считаются в аналитике по
уникальным сессиям.

|---|---|
| Публичный URL | <https://funnelserver-production.up.railway.app> |
| Репозиторий | <https://github.com/scrollDynasty/test_assignment> |
| Воронка | [`/f/workstyle-planner`](https://funnelserver-production.up.railway.app/f/workstyle-planner) (`?variant=A\|B` — принудительный вариант, `utm_*` — метки, `?lang=ru\|en`) |
| Внутренний раздел | [`/internal/analytics`](https://funnelserver-production.up.railway.app/internal/analytics), [`/internal/versions`](https://funnelserver-production.up.railway.app/internal/versions) — вход по ключу доступа (ключ — в письме к сдаче) |
| Журнал решений | [WORKLOG.md](WORKLOG.md) — решения D1–D37 и семь раундов независимого ревью с разбором находок |

## Проверить за 5 минут

1. **Воронка** `/f/workstyle-planner`: ответьте на пару вопросов и обновите страницу — шаг и ответы на месте. Назад —
   «← Назад» в углу (мышь), свайп вправо (телефон) или «назад» браузера. «Гибридно» или «В основном в офисе» открывает
   условный вопрос про дни в офисе. `?variant=B` — принудительный вариант (новая сессия, по умолчанию не входит в
   A/B), `?debug=1` — показать версию и вариант. UTM фиксируются при первом заходе; новую метку проверяйте в
   приватном окне или после «Начать заново».
2. **Внутренний раздел** `/internal`: ключ доступа из письма (локально — `dev-admin-token`).
3. **Аналитика** `/internal/analytics`: после генератора выключите окно «в процессе» (подсказка появится сама), иначе
   свежие сессии считаются «в процессе», а не отвалами. Переключайте версии и кампании.
4. **Версии** `/internal/versions`: активная версия и её JSON, журнал релизов, публикация и откат, отпечаток схемы БД.
5. **Трафик и сценарий итерации против любого инстанса:**
   ```bash
   ADMIN_TOKEN=<ключ> npm run traffic -- --url https://funnelserver-production.up.railway.app --sessions 150 --verify
   ADMIN_TOKEN=<ключ> npm run demo:iteration -- --url https://funnelserver-production.up.railway.app --config funnel-v3.json --traffic 150
   ```

## Отступления от ТЗ и спорные трактовки

- **Прогресс** — тонкая линия вверху без цифр («2 из 6» посетитель не видит). Считается по ТЗ: только доступные
  пользователю шаги (`computeProgress`); открывшаяся ветка замедляет рост линии, а не превращает «2 из 6» в «2 из 7».
- **Назад** на тач-экранах — свайп (плюс одноразовая подсказка) и системный жест; на компьютере — ссылка в углу.
  Все пути идут через историю браузера: одно событие `back_clicked`, одно поведение.
- **«Конверсия между шагами»** = прошли шаг / видели шаг, а не «шаг N → N+1»: с условными шагами следующий шаг
  не определён однозначно (см. правила агрегации).
- **Русский перевод контента** — словарь по исходному английскому тексту в коде сайта (конфиги менять нельзя). Экраны
  при этом не захардкожены; новая фраза в новой версии конфига без перевода показывается в оригинале.
- **v3 была в репозитории с начала** и проверялась движком уже в итерации 1; «вслепую» написана только доработка
  итерации 2 (момент отправки `recommendation_expanded`).

## Запуск

Нужен Node.js 22+.

```bash
npm ci
npm run dev                                # API :3000 (ключ dev-admin-token) + сайт :5173
npm test                                   # 261 автотест (Vitest); e2e и Docker — см. «Как проверено»
npm run typecheck && npm run lint          # строгий TypeScript по всем пакетам, ESLint (any запрещён)
npm run traffic -- --sessions 150 --verify # синтетический трафик + сверка дашборда с ground truth
npm run publish-config -- funnel-v2.json   # загрузить и опубликовать версию (API_URL, ADMIN_TOKEN из env)
npm run publish-config -- --rollback       # откатить последнюю публикацию
npm run demo:iteration -- --config funnel-v2.json --traffic 150   # сценарий итерации с проверками
npm run db:schema-hash                     # отпечаток схемы БД
```

При пустой базе сервер сам загружает и публикует `funnel-v1.json`; база — `data/funnel.db`.

> Windows: если `npm ci` не собирает `better-sqlite3`, выполните `npx node-gyp@latest rebuild --release` в
> `node_modules/better-sqlite3`. В Docker используется готовый бинарник.

### Docker и хостинг

```bash
docker build -t funnel-runtime .
docker run -p 8080:8080 -v funnel-data:/data --env-file .env funnel-runtime   # .env: ADMIN_TOKEN=<ключ>
```

| Переменная | Значение |
|---|---|
| `ADMIN_TOKEN` | ключ внутреннего раздела, 16+ символов, иначе сервер не стартует. Не зашивается в образ — задаётся при запуске. Сгенерировать: `node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"`. Смена ключа разлогинивает всех |
| `TRUST_PROXY` | число обратных прокси перед приложением. **За Railway и подобными — `1`**, иначе все посетители делят один лимит запросов |
| `DB_PATH` | путь к SQLite; в образе `/data/funnel.db` (volume) |
| `PORT` | задаёт платформа; по умолчанию 8080 в образе |
| `PUBLIC_RATE_LIMIT` | запросов в минуту с IP на публичный API, по умолчанию 600; создание сессий — десятая часть (60). Запросы с ключом доступа (генератор, демо) не ограничиваются |

**CI/CD:** GitHub Actions (`.github/workflows/ci.yml`) на каждый push и pull request: типы, линтер, тесты с порогами
покрытия, E2E, сборка и smoke-тест Docker-образа; аудит зависимостей — отдельный `audit.yml` (подробнее — «Как
проверено»). Railway следит за веткой `master` и с опцией «Wait for CI» выкатывает
коммит только после зелёного CI.

**Railway:** сборка из `Dockerfile`, health-check `GET /api/health` (проверяет и БД), перезапуск при сбое, пересборка
только при изменении кода (правка документации не перезапускает сайт); те же настройки записаны в `railway.json`
(Railway больше не подключает config-as-code к новым сервисам, поэтому они заданы и в интерфейсе). Volume с mount path
`/data`, переменные `ADMIN_TOKEN` и `TRUST_PROXY=1`, одна реплика (SQLite — один процесс).
Контейнер сам отдаёт `/data` пользователю `node` и работает не от root. Бэкапы — снапшоты volume в Railway
(`npm run db:backup` делает целостную копию локально).

### Обновление без заметного простоя

ТЗ требует SQLite (или файлы) и запрещает сторонние сервисы, поэтому приложение — один процесс, владеющий файлом базы.
Настоящий blue-green (две копии за балансировщиком) требует, чтобы обе копии писали в одну базу: на одной машине это
возможно (SQLite в режиме WAL безопасен для нескольких процессов одного хоста), но Railway подключает volume только к
одному запущенному контейнеру и при деплое сначала останавливает старый. Сетевая БД (Postgres) решила бы это, но
нарушает ТЗ. Поэтому цель — не «ноль секунд перезапуска», а **ноль заметного для посетителя простоя**:

| Звено | Что происходит при деплое |
|---|---|
| Анкета и A/B | меняются публикацией конфига — **без перезапуска вообще** (основной способ обновлять продукт) |
| Сервер | по SIGTERM перестаёт принимать новые соединения, отвечает на health 503, дорабатывает начатые запросы, закрывает SQLite; новый стартует за ~1 с (замер локально) и получает трафик только после успешного health-check |
| Страница | service worker держит в кэше оболочку сайта и файлы текущей версии: перезагрузка во время перезапуска открывает сайт, а не ошибку; старые файлы остаются доступны уже открытым вкладкам |
| Переходы по анкете | считаются в браузере общим движком — работают и без сервера |
| Сохранение ответов, события | очереди с повторами (сохранение — до ~30 с, события — пока не доставлены); создание сессии, загрузка сессии и результат повторяются до ~15 с (идемпотентно) |

Проверено на production-сборке локально: сервер выключен → ответ на вопрос, переход и перезагрузка страницы без
ошибок → сервер включён → ответ сохранился на сервере, очередь событий пуста.

## Архитектура

```
funnel-v1/v2/v3.json   конфиги заказчика, не редактируются (sha256 в WORKLOG)
packages/shared        общий движок: условия, варианты, навигация, прогресс, валидация, результат, правила событий;
                       zod-схемы конфига и запросов (только сервер); браузер получает вход без zod (client.ts)
apps/server            Fastify + better-sqlite3: версии, сессии, приём событий, аналитика; раздаёт и собранный сайт
apps/web               React + Vite: рантайм воронки; дашборд и админка грузятся отдельно, только во внутреннем разделе
scripts                генератор трафика, сценарий итерации, публикация конфига, отпечаток схемы, бэкап
```

Один код движка работает в браузере (мгновенный отклик) и на сервере (перепроверка состояния, расчёт результата),
поэтому сайт и сервер не расходятся в логике воронки.

**Рендер без хардкода экранов.** Один компонент на *тип* шага (`info`, `single-select`, `multi-select`, `number`,
`result`); тексты, варианты, лимиты и сообщения об ошибках — из конфига. Вариант = `stepSequence` + частичные
`stepOverrides`/`resultOverrides`. Условия — рекурсивный DSL (`all/any/not` + `eq, neq, in, not_in, gt, gte, lt, lte,
contains, exists`) с трёхзначной логикой: неотвеченный вопрос никогда не открывает ветку. Ответ скрытого шага хранится,
но не влияет на результат и прогресс.

**Проверка конфига при загрузке** (иначе 422, активная версия не меняется) идёт по тому, что показывает *каждый
вариант* после overrides: ссылки на шаги и результаты, один `result` в конце, условия смотрят только назад и совместимы
с типом и вариантами вопроса, уникальные имена ответов, и каждый вопрос выполним (`min ≤ max`, `minSelections` не
больше числа вариантов и т.п.) — опубликованная версия не может запереть сессию на шаге.

## Модель данных (SQLite)

| Таблица | Назначение |
|---|---|
| `funnel_versions` | неизменяемые снимки `(funnel_id, version)`: JSON как есть + sha256 канонического JSON (без `status`). Тот же файл повторно — no-op, тот же номер с другим содержимым — 409 |
| `funnel_active` | указатель: на какой версии создаются **новые** сессии |
| `release_log` | публикации и откаты (только INSERT); откат = отмена последней неотменённой публикации (стек) |
| `sessions` | закреплённые навсегда `funnel_version`, `experiment_id`, `variant`, `assignment` (`hash`/`override`), first-touch UTM, `state_json` (ответы, путь, текущий шаг), `state_rev` (optimistic lock), статус и `result_id`, `expires_at` (TTL из конфига, 72 ч) |
| `events` | `event_id` PK; имя, шаг, **контекст из сессии** (версия, вариант, assignment, UTM), `client_ts`, `server_ts`, `seq`, свойства JSON |
| `ingest_log` | по строке на пачку: принято / дублей / отклонено + причины |
| `schema_migrations` | миграции применяются при старте (за весь проект — одна) |

**Почему новая версия не требует миграции.** Всё, что специфично для версии (шаги, результаты, условия, список
событий), лежит в `config_json`; новая версия — одна строка. Публикация и откат меняют только указатель; версии не
удаляются, поэтому сессия любой версии находит свой конфиг, а аналитика любой версии сохраняется. Доказательство —
отпечаток схемы (`GET /api/admin/schema`, `npm run db:schema-hash`) одинаков до и после.

## Сессии, версии и A/B

- Новая сессия создаётся на активной версии; версия и вариант закреплены за ней навсегда — и после публикации, и после
  отката. Страница передаёт ключ идемпотентности: повтор запроса после потерянного ответа возвращает ту же сессию, а не
  второй `session_started`.
- Вариант назначает сервер: `sha256(experiment_id:session_id)` по весам. Id сессии сервер выводит сам (uuid v5 от ключа
  в своём секретном пространстве имён), поэтому клиент не может подобрать себе вариант. `?variant=B` действует только
  при создании сессии, помечается `assignment = override` и по умолчанию не входит в A/B.
- Откат отменяет последнюю неотменённую публикацию: v1 → v2 → v3 → откат → откат даёт v2, затем v1. Ничего не удаляется.

## События

`POST /api/events`, `{ "events": [...] }`, до 100 штук. Поля — из `events.baseProperties` конфига: `event_id` (uuid),
`session_id`, `name`, `client_timestamp`, `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `step_id`,
`utm_source`, `utm_medium`, `utm_campaign`, плюс `seq` (счётчик внутри сессии) и `properties`. `server_timestamp`
ставит сервер.

| Событие | Когда | Свойства |
|---|---|---|
| `session_started` | сервер, в одной транзакции с созданием сессии, id = uuid v5(session_id) | — |
| `step_viewed` | шаг отрисован (в т.ч. повторно после «назад»/refresh) | `step_type`, `visible_step_index`, `visible_step_count` |
| `answer_submitted` | валидный ответ отправлен | `answer_kind` — **без значения ответа** |
| `step_completed` | переход вперёд с интерактивного шага | `next_step_id` |
| `back_clicked` | «назад» любым способом (ссылка, свайп, браузер — один путь кода через историю) | `destination_step_id` |
| `result_viewed` | результат отрисован | `result_id` |
| `cta_clicked` | клик по основной кнопке результата | `result_id`, `action` |
| `recommendation_expanded` (v3) | раскрытые рекомендации отрисованы после CTA; шлётся, только если событие объявлено версией сессии | `result_id`, `action`, `source` |

**Инварианты приёма:**
- **Идемпотентность:** `INSERT … ON CONFLICT(event_id) DO NOTHING` — первая запись побеждает; повтор пачки возвращает
  `duplicate` и ничего не меняет (upsert отвергнут: ретрай с другим payload перезаписал бы факт).
- **Пачка:** ответ 200 со статусом каждого события (`accepted` / `duplicate` / `rejected{reason}`); битое событие не
  ломает остальные. Больше 100 — 413, неправильный запрос целиком — 400.
- **Контекст из сессии:** версию, вариант и UTM сервер берёт из сессии; несовпадение — `context_mismatch`. Событие и
  значения свойств сверяются с версией сессии; время клиента — в пределах −30 дней … +1 день.
- **Результат нельзя «заявить»:** `result_viewed` и `cta_clicked` принимаются только с шага-результата и только у
  сессии, чьи сохранённые ответы действительно ведут к результату (`result_not_reached`), — иначе клиент мог бы
  накрутить основную метрику A/B. Шаговые события без `step_id` отклоняются (`missing_step`); `event_id` сравнивается
  без учёта регистра.
- **Приватность:** свойства режутся whitelist'ом из конфига, значения ответов в события не попадают. Сырые ответы — только
  в `sessions.state_json` (нужны для продолжения) и стираются после TTL; id сессий в логах маскируются.
- **Клиент:** outbox в localStorage, пачки по количеству и байтам (< 48 КБ, лимит keepalive), повторы с backoff,
  отправка при уходе со страницы; событие удаляется только после ответа сервера → at-least-once + дедуп = exactly-once.

## Правила агрегации (всё — уникальные сессии)

| Показатель | Определение |
|---|---|
| Начали | сессии с `session_started` в фильтре (версия, кампания; override-сессии исключены по умолчанию) |
| Просмотрели шаг | есть `step_viewed`, `answer_submitted` или `step_completed` по шагу (поздние события доказывают просмотр) |
| Прошли шаг | интерактивный — `step_completed`; info — просмотрен более поздний шаг или достигнут результат |
| Конверсия шага | прошли / просмотрели (условный шаг не выглядит потерей) |
| Охват шага | просмотрели / начали |
| Дошли до результата | `result_viewed` **или** `cta_clicked` (клик доказывает показ → CTR ≤ 100%) **или** результат посчитан сервером (все ответы даны — потерянный `result_viewed` не превращает прошедшего в «отвал») |
| Отвал на шаге | не дошли, не «в процессе», и **самый дальний** просмотренный шаг (по позиции в последовательности своего варианта) — этот; отдельно — ушли до первого экрана |
| В процессе | не дошли, сессия не истекла, последняя активность в пределах окна (по умолчанию 30 мин, на дашборде можно выключить) |
| CTR CTA | кликнули / дошли |
| Start → CTA | кликнули / начали — **основная метрика A/B** |

**Проверяемый инвариант** (на дашборде у каждого варианта): Σ отвалов + ушли до первого экрана + дошли + в процессе
= начали = число сессий того же фильтра в таблице `sessions` (посчитано без событий — ловит потерянный или лишний
`session_started`).

Все показатели — множества сессий: дубль не проходит первичный ключ, повторный просмотр не меняет множество, «самый
дальний шаг» не зависит от порядка прихода по построению. Порядок нужен только для последнего результата сессии, и
основной источник — результат, посчитанный сервером (`sessions.result_id`).

Дашборд также показывает: A/B (Wilson 95% CI, разница с CI Ньюкомба, p-value z-теста, MDE, проверка SRM χ²),
предупреждение при < 30 сессий в группе, распределение результатов, сравнение версий, прочие события версии,
качество данных (дубли, отклонённые по причинам).

## A/B-гипотеза и основная метрика

**Что отличает B** (в конфигах): первым идёт простой вопрос («где работает команда»), тяжёлый числовой ввод размера
команды перенесён глубже; результат подан как действие («See the 30-day action list»). В v3 у B ещё убран `tool_count`.

**Гипотеза:** лёгкое начало и меньше шагов, не влияющих на результат, — меньше отвалов, а подача результата как плана
действий повышает клик. Ожидаем рост **start → CTA** у B.

**Почему start → CTA.** B меняет и дохождение, и клик. Голый CTR смещён: он считается только по дошедшим, а в B доходят
другие люди. Start → CTA учитывает оба эффекта и отвечает на вопрос «сколько из пришедших получили план действий».
Рядом — completion и распределение результатов: B только переставляет вопросы, поэтому результаты в A и B должны
распределяться похоже; перекос — признак эффекта порядка или бага.

**Наблюдение по данным.** `team_size`, `office_days` и `tool_count` не участвуют ни в одном правиле результата ни в
одной версии — кандидаты на удаление; B в v3 проверяет это для `tool_count`.

**Как читать результат.** При ~75 сессиях на группу надёжно заметна только разница порядка 17–23 п.п. (MDE — на
дашборде); «не значимо» не значит «нет эффекта». B объединяет несколько изменений, поэтому выигрыш нельзя приписать
одному из них; подача CTA у B различается между версиями, так что эксперименты разных версий не складываются.

| Часть | Доступ | Защита |
|---|---|---|

Ключ вводится один раз → подписанная cookie `HttpOnly; SameSite=Strict; Secure` на 8 ч; ключ не хранится ни в коде
страницы, ни в localStorage. Скрипты шлют `x-admin-token`. Вход — 20 попыток/мин с IP; неверный ключ в заголовке — тот же общий бюджет 20/мин
с IP на любом адресе (иначе заголовок стал бы обходом лимита входа); «вошёл ли я» проверяет только cookie. Изменяющие запросы к внутреннему API с чужого сайта (`Sec-Fetch-Site` /
`Origin`) отклоняются; проверка смотрит на найденный маршрут, поэтому `%61dmin` её не обходит. CSP `default-src 'self'` (шрифты свои, без CDN), HSTS, `frame-ancestors 'none'`. Посетитель не
видит ссылок на внутренний раздел и свой вариант эксперимента.

**CI** (`.github/workflows/ci.yml`, на каждый push и pull request, 4 параллельные задачи): типы + линтер;
модульные/property/интеграционные/компонентные тесты с порогами покрытия и отчётом; E2E на production-сборке с

дисциплина, а жёсткий барьер — Railway, который выкатывает `master` только после зелёного CI.

## Ограничения и допущения

- SQLite — один процесс и одна реплика (single writer); горизонтальное масштабирование не предусмотрено. На Railway
  volume означает короткий простой при каждом деплое; клиент переживает его (outbox и сохранение повторяются).
- Отчёт аналитики считается на лету и синхронно: замер на синтетической базе — ~10 тыс. сессий ≈ 0,5 с, ~50 тыс. —
  4–6 с, и на это время блокируется приём событий. Следующий шаг — расчёт в `worker_thread` на read-only соединении (WAL позволяет) и
  сводная таблица по сессиям, обновляемая при приёме.
- Вариант закреплён за сессией, а не за человеком: новая сессия (другой браузер, «Начать заново», истёк TTL) может
  попасть в другой вариант.
- A/B считается по завершённым сессиям и без заранее заданного размера выборки: дашборд показывает MDE и предупреждает
  о малой выборке, но защиты от «подглядывания» нет — в продакшене нужен план выборки или последовательный тест.
- Откат не переводит сессии, уже начатые на откатываемой версии. «Аварийная блокировка» версии (такие сессии получают
  410 и начинают заново) требует колонки, т.е. миграции, поэтому не делалась в рамках «схема не менялась».
- `recommendation_expanded` почти всегда совпадает с `cta_clicked` в текущем UI — это прочтение формулировки конфига;
  какое действие должно его вызывать, стоит решить с продуктом.
- Выход удаляет cookie, но подписанная сессия без состояния на сервере не отзывается до истечения 8 ч; смена ключа
  разлогинивает всех. Один общий ключ без ролей — для продакшена нужен SSO.
- «В процессе» определяется по времени прихода событий на сервер; поздний ретрай ненадолго возвращает брошенную сессию в
  «в процессе». `--verify` генератора сравнивает дельту отчёта до/после — верно только на «тихом» инстансе.
- `next_step_id` / `destination_step_id` косвенно показывают выбранную ветку — оставлены, так как их требует конфиг.
- Шаг условной ветки, которую посетитель открыл, а потом закрыл возвратом назад (выбрал «Гибридно», увидел
  `office_days`, вернулся и выбрал «Удалённо»), остаётся на дашборде «просмотренным, но не пройденным». Точная
  поправка требует знать итоговые ответы, а они стираются после TTL, поэтому не делалась.
- С экрана результата нет кнопки «Назад»: это конец анкеты, в том числе для вернувшегося позже посетителя. «Назад»
  браузера возвращает к последнему вопросу, и ответ можно изменить (результат пересчитается).
- Поле `status` в конфигах (`draft`/`published`) игнорируется: активность версии хранит сервер.
