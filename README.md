# Funnel Runtime

Мини-платформа для многошаговых веб-воронок: экраны описываются JSON-конфигом, у конфига есть версии с публикацией и
откатом без передеплоя, внутри версии работает A/B-эксперимент, события собственного endpoint'а считаются в аналитике по
уникальным сессиям. Тестовое задание — см. [TZ.md](TZ.md).

| | |
|---|---|
| Публичный URL | _будет добавлен после деплоя на Fly.io_ |
| Воронка | `/f/workstyle-planner` (`?variant=A\|B` — принудительный вариант, `utm_*` — метки) |
| Аналитика | `/analytics` — публичная, только агрегаты |
| Версии | `/admin` — под токеном `x-admin-token` |
| Журнал решений | [WORKLOG.md](WORKLOG.md) — каждое решение с обоснованием, ревью и что с ними сделано |
| Отчёт демо итерации 1 | [docs/iteration-1-demo.md](docs/iteration-1-demo.md) |

## Быстрый старт

Нужен Node.js 22+.

```bash
npm ci
npm run dev          # API на :3000 (с --dev, токен админки: dev-admin-token) + сайт на :5173
```

Открыть http://localhost:5173. При пустой базе сервер сам загружает и публикует `funnel-v1.json`; база — `data/funnel.db`.

```bash
npm test                                   # 123 автотеста (Vitest)
npm run typecheck && npm run lint          # строгий TypeScript по всем пакетам, ESLint (any запрещён)
npm run traffic -- --sessions 150 --verify # синтетический трафик + сверка дашборда с ground truth
npm run publish-config -- funnel-v2.json   # загрузить и опубликовать версию в работающий инстанс
npm run publish-config -- --rollback       # откатить последнюю публикацию
npm run demo:iteration -- --config funnel-v2.json --traffic 150   # весь сценарий итерации с проверками
npm run db:schema-hash                     # отпечаток схемы БД
```

Как в проде (один контейнер, SQLite на volume):

```bash
docker build -t funnel-runtime .
docker run -p 8080:8080 -v funnel-data:/data -e ADMIN_TOKEN=<16+ символов> funnel-runtime
```

> Windows: если `npm ci` не может собрать `better-sqlite3` (нет готового бинарника под вашу связку Node/Visual Studio),
> соберите его вручную: `npx node-gyp@latest rebuild --release` в `node_modules/better-sqlite3`. В Docker (Linux)
> используется готовый бинарник.

## Архитектура

```
funnel-v1/v2/v3.json   конфиги заказчика, не редактируются (sha256 в WORKLOG)
packages/shared        общий «движок» воронки: zod-схема конфига, условия, варианты, навигация, прогресс,
                       валидация ответов и состояния, расчёт результата, схема события, типы API и отчёта
apps/server            Fastify + better-sqlite3: версии, сессии, приём событий, аналитика; в проде раздаёт и SPA
apps/web               React + Vite: рантайм воронки, дашборд, админка версий
scripts                генератор трафика, сценарий демо итерации, публикация конфига, отпечаток схемы
```

Один и тот же код из `packages/shared` работает в браузере (мгновенный отклик) и на сервере (перепроверка состояния,
расчёт результата) — поэтому сайт и сервер не могут разойтись в логике воронки.

**Рендер без хардкода экранов.** Есть один компонент на *тип* шага (`info`, `single-select`, `multi-select`, `number`,
`result`); тексты, варианты, лимиты и сообщения об ошибках — из конфига. Вариант собирается как `stepSequence` +
частичные `stepOverrides`/`resultOverrides`. Условия — рекурсивный DSL (`all/any/not` + `eq, neq, in, not_in, gt, gte,
lt, lte, contains, exists`) с трёхзначной логикой: неотвеченный вопрос никогда не открывает ветку. Следующий шаг —
первый видимый дальше по последовательности; ответ скрытого шага хранится, но не влияет на результат и прогресс.
Прогресс считает только видимые вопросы (при открытии ветки знаменатель растёт честно).

**Валидация конфига при загрузке** (иначе 422, активная версия не меняется) проверяет то, что реально показывает
*каждый вариант* после overrides: ссылки на шаги/результаты, один `result` в конце, условия ссылаются только на ранее
заданные вопросы, значения условий совместимы с типом и опциями вопроса, уникальность input-имён.

## Модель данных (SQLite)

| Таблица | Назначение |
|---|---|
| `funnel_versions` | неизменяемые снимки конфигов `(funnel_id, version)`, JSON как есть + sha256 канонического JSON. Тот же файл повторно — no-op, тот же номер с другим содержимым — 409 |
| `funnel_active` | указатель: на какой версии создаются **новые** сессии |
| `release_log` | журнал публикаций и откатов (только INSERT); откат = отмена последней неотменённой публикации (стек) |
| `sessions` | сессия с закреплёнными навсегда `funnel_version`, `experiment_id`, `variant`, `assignment` (`hash`/`override`), first-touch UTM, `state_json` (ответы, путь, текущий шаг), `state_rev` (optimistic lock), статус и `result_id`, `expires_at` (TTL из конфига, 72 ч) |
| `events` | `event_id` PK; имя, шаг, **контекст из сессии** (версия, вариант, assignment, UTM), `client_ts`, `server_ts`, `seq`, свойства JSON |
| `ingest_log` | по строке на пачку: принято / дублей / отклонено + причины |
| `schema_migrations` | миграции применяются автоматически при старте |

**Почему схема переживает новую версию без миграций.** Всё, что специфично для версии (шаги, результаты, условия,
список событий), лежит в `config_json`. Новая версия — одна новая строка. Публикация и откат меняют только указатель;
версии не удаляются, поэтому сессия любой версии всегда находит свой конфиг, а аналитика любой версии сохраняется.
Доказательство — отпечаток схемы (`GET /api/admin/schema`, `npm run db:schema-hash`) одинаковый до и после.

## События

### Схема (`POST /api/events`, `{ "events": [...] }`, до 100 штук)

Поля совпадают с `events.baseProperties` конфига: `event_id` (uuid), `session_id`, `name`, `client_timestamp`
(ISO или ms), `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `step_id`, `utm_source`, `utm_medium`,
`utm_campaign`, плюс `seq` (счётчик внутри сессии) и `properties`. `server_timestamp` ставит сервер.

| Событие | Когда | Свойства |
|---|---|---|
| `session_started` | сервер, в одной транзакции с созданием сессии, id = uuid v5(session_id) | — |
| `step_viewed` | шаг отрисован (в т.ч. повторно после back/refresh) | `step_type`, `visible_step_index`, `visible_step_count` |
| `answer_submitted` | валидный ответ отправлен | `answer_kind` (`single_select`/`multi_select`/`number`) — **без значения ответа** |
| `step_completed` | переход вперёд с интерактивного шага | `next_step_id` |
| `back_clicked` | «назад» в интерфейсе или в браузере (один путь кода) | `destination_step_id` |
| `result_viewed` | результат отрисован | `result_id` |
| `cta_clicked` | клик по основной кнопке результата | `result_id`, `action` |

### Инварианты приёма

- **Идемпотентность:** `INSERT … ON CONFLICT(event_id) DO NOTHING` — первая запись побеждает; повтор той же пачки после
  таймаута возвращает `duplicate` и ничего не меняет (upsert отвергнут: ретрай с другим payload перезаписал бы факт).
- **Пачка:** ответ всегда 200 со статусом каждого события (`accepted` / `duplicate` / `rejected{reason}`); одно битое
  событие не ломает остальные. Больше 100 событий — 413, неправильный запрос целиком — 400.
- **Контекст из сессии:** версию, вариант, UTM сервер берёт из сессии, а не из события; несовпадение — `context_mismatch`.
- **Разрешено версией:** событие и его свойства сверяются с `events.allowed` **версии сессии**; новое событие новой
  версии принимается только от её сессий.
- **Приватность:** свойства режутся whitelist'ом из конфига, значения ответов в события не попадают. Сырые ответы живут
  только в `sessions.state_json` (нужны для продолжения сессии) и стираются после истечения TTL.
- **Клиент:** outbox в localStorage, пачки по количеству и байтам (<48 КБ — лимит keepalive), ретраи с backoff,
  отправка при уходе со страницы. Событие удаляется из outbox только после ответа сервера → at-least-once + дедуп = exactly-once в таблице.
- Публичные write-эндпоинты ограничены по IP (по умолчанию 3000/мин), админка — 120/мин.

## Правила агрегации (всё — уникальные сессии)

| Показатель | Определение |
|---|---|
| Начали | сессии с `session_started` в фильтре (версия, кампания, override-сессии исключены по умолчанию) |
| Просмотрели шаг | есть `step_viewed` **или** `answer_submitted` **или** `step_completed` по шагу (поздние события доказывают просмотр) |
| Прошли шаг | интерактивный — `step_completed`; info — просмотрен любой более поздний шаг или достигнут результат |
| Конверсия шага | прошли / просмотрели (к шагу, а не к предыдущему: условный шаг не выглядит потерей) |
| Охват шага | просмотрели / начали |
| Дошли до результата | `result_viewed` **или** `cta_clicked` (клик доказывает показ → CTR ≤ 100%) |
| Отвал на шаге | не дошли до результата, не «в процессе», и **самый дальний** просмотренный шаг (по позиции в последовательности своего варианта) — этот. Отдельно: ушли до первого экрана |
| В процессе | не дошли, сессия не истекла, последняя активность в пределах окна (по умолчанию 30 мин, на дашборде можно выключить) |
| CTR CTA | кликнули / дошли до результата |
| Start → CTA | кликнули / начали — **основная метрика A/B** |

**Проверяемый инвариант:** Σ отвалов + ушли до первого экрана + дошли + в процессе = начали (выводится на дашборде).

**Почему дубли, повторы, «назад» и порядок прихода не влияют:** все показатели — это множества сессий; дубль не проходит
первичный ключ, повторный просмотр не меняет множество, «самый дальний шаг» не зависит от порядка по построению.
Единственное место, где нужен порядок, — выбор последнего результата сессии; он идёт по клиентскому `seq`.

Дашборд также показывает: сравнение A/B (Wilson 95% CI, разница с CI Ньюкомба, p-value z-теста, минимально детектируемый
эффект, проверка SRM χ²), предупреждение при <30 сессий в группе, распределение результатов по вариантам, сравнение
версий, прочие события версии, качество данных (дубли, отклонённые по причинам) и сверку «завершили по серверу / по событиям».

## A/B-гипотеза и основная метрика

**Что отличает B** (в конфигах заказчика): вопросы идут в другом порядке — первым простой вопрос-идентичность
(«где работает команда»), тяжёлый числовой ввод размера команды перенесён глубже; результат подан как действие
(«See the 30-day action list» и т.п.). В v3 у B ещё и убран вопрос `tool_count`.

**Гипотеза:** если начинать с лёгкого вопроса и убирать шаги, не влияющие на результат, меньше людей бросит анкету, а
подача результата как плана действий повысит клик. Ожидаем рост **start → CTA** у B.

**Почему именно start → CTA.** B меняет *и* дохождение (порядок и длина), *и* клик (подача результата). Голый CTR
смещён: он считается только по дошедшим, а в B доходят другие люди. Start → CTA учитывает оба эффекта и отвечает на
бизнес-вопрос «сколько из пришедших получили план действий». Для диагностики рядом — completion и распределение
результатов: B только переставляет вопросы, поэтому результаты в A и B должны распределяться похоже; перекос — признак
эффекта порядка или бага.

**Наблюдение по данным.** `team_size`, `office_days` и `tool_count` не участвуют ни в одном правиле результата ни в одной
версии — это кандидаты на удаление; B в v3 проверяет как раз это для `tool_count`.

**Как читать результат.** При ~75 сессиях на группу надёжно заметна только разница порядка 17–19 п.п. — дашборд пишет
это явно; «не значимо» не значит «нет эффекта». B объединяет несколько изменений, поэтому выигрыш нельзя приписать
одному из них; подача CTA у B различается между версиями, так что эксперименты разных версий не складываются.

## Версии и откат

- Загрузка (`POST /api/admin/funnels/:id/versions`) валидирует и сохраняет, но ничего не меняет для пользователей.
- Публикация делает версию активной для **новых** сессий. Начатые сессии дописываются на своей версии — и после
  публикации, и после отката (решение согласовано с заказчиком).
- Откат отменяет последнюю неотменённую публикацию: v1→v2→v3→откат→откат даёт v2, затем v1. Ничего не удаляется.
- Вариант назначается на сервере детерминированным хешем `sha256(experiment_id:session_id)` по весам и хранится в
  сессии. `?variant=B` действует только при создании сессии; если открыта сессия другого варианта — создаётся новая,
  старая не меняется. Такие сессии помечены и по умолчанию не входят в A/B.

## Как проверено

- **123 автотеста**: движок на реальных v1/v2/v3 и на специально сломанных конфигах (74), версии (7), сессии (11),
  события (8), аналитика (10), статистика (10), эксплуатация (3). Пять обязательных из п.7.1: закрепление версии,
  стабильность A/B, дедупликация, публикация и откат, расчёт аналитики (включая инвариантность к перестановке событий).
- **Мутационные проверки** тестов (намеренно ломал код — соответствующие тесты падали): закрепление версии,
  детерминизм A/B, «первая запись побеждает».
- **Генератор с `--verify`**: 150 сессий, повторные пачки, перемешанные и переставленные пачки, битые события —
  все проверяемые показатели дашборда (started, reached, CTA, отвал и просмотры по каждому шагу, back) совпадают с
  независимым расчётом генератора.
- **Ручная проверка в браузере**: валидация с текстами из конфига, ветвление, refresh посреди анкеты, «назад»/«вперёд»
  браузера, досылка несохранённого шага после перезагрузки, результат и CTA.
- **Два независимых ревью агентами** без доступа к журналу решений; все находки и решения по ним — в WORKLOG.

## Ограничения и допущения

- Публичный URL ещё не развёрнут (ожидает аккаунта Fly.io); демо итерации 1 прогнано на том же Docker-образе локально.
- SQLite — один процесс и одна машина (single writer); для этой нагрузки достаточно, горизонтальное масштабирование не предусмотрено.
- Вариант закреплён за сессией, а не за человеком: новая сессия (другой браузер, «Start again», истёк TTL) может попасть в другой вариант.
- Отчёт аналитики считается на лету при каждом запросе (без кэша) — нормально для десятков тысяч сессий, не больше.
- `ingest_log` общий для всех воронок (в проекте одна воронка).
- «В процессе» определяется по времени прихода событий на сервер; поздний ретрай ненадолго возвращает брошенную сессию в «в процессе».
- `next_step_id` / `destination_step_id` косвенно показывают выбранную ветку (например, пропуск `office_days` ⇒ удалёнка) — оставлены, так как их требует конфиг.
- Публичная аналитика: любой может создать сессию и отправить события своей сессии — защищаемся лимитами по IP, не аутентификацией.
- Поле `status` в конфигах (`draft`/`published`) игнорируется: активность версии хранит сервер.
- Интерфейс воронки на английском, как тексты конфигов (`locale: en-AU`); служебные страницы тоже на английском.
